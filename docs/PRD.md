# 本体工程与语义应用工作台 PRD

版本：0.2｜更新：2026-09-06｜状态：规划评审稿，尚未实施

本文件替代 v0.1 与其 Foundry 增补章节，统一产品范围和优先级。实施排期以 [里程碑计划](MILESTONES.md) 为准；[旧稿](archive/PRD-v0.1.md) 仅供追溯。文中指标是待验证目标，不是现有能力或性能声明。

## 1. 产品定位与交付价值

面向制造业轻量 FDE 团队的本体工程工作台与轻量语义应用交付平台。将客户需求、现场术语、数据和文档转化为有证据、可审核、可验证的本体，再按项目需要交付对象浏览、业务动作和操作页面。

产品服务两个同等重要的目标：

1. 帮助 FDE 快速完成客户项目：减少资料整理、字段解释、映射调试、重复演示和现场部署时间。
2. 沉淀团队资产：让行业概念、规则、映射、查询和应用配置可以跨项目复用，并保留客户私有边界。

基本交付单元是“用例包”：业务问题 + 本体 + 映射 + 验收查询 + 来源证据 + 运行配置；后续按阶段加入对象视图、动作和自动化。

## 2. 规划假设与范围边界

以下为排期假设，需在项目启动时核实：

| 项目 | 基线假设 |
|---|---|
| 人员 | 4 名全职工程师；产品/FDE 负责人投入 0.3–0.5 FTE；领域专家每周 2–4 小时 |
| 节奏 | 24 个相对工作周；W1 为实际启动周，不假定已经开工 |
| 首个场景 | 离散制造质量异常追溯：批次/工单 → 工序/设备 → 检验/缺陷 → 内部处理任务 |
| 试点范围 | 1 个客户、1 个闭环、2 类数据源、3 个业务验收查询 |
| 部署 | 单租户、多项目；Docker Compose 起步，客户私有化为优先交付方式 |
| 输入 | MVP 使用 CSV/XLSX、文本/Markdown、PostgreSQL；其他 SQL 通过后续连接器扩展 |
| AI | 先接入 1 个获准使用的模型；手工与规则路径可独立工作 |
| 客户配合 | 有数据负责人、脱敏样本、只读接入条件、固定领域评审与验收窗口 |

24 周基线暂不包含：通用低代码平台、多租户 SaaS、完整 MES/ERP、自动生产系统写回、PLC/设备控制、实时 IoT 平台、扫描件 OCR、任意第三方插件执行、完整 OWL DL 推理、完整 Git 式三路合并和实时多人协作。

模型与部署条件不同的客户，通过调整 profile 和连接器适配。完全离线环境在 M3 验证，不能由“可私有化”推断为已支持离线安装或离线模型。

## 3. 成功定义

- FDE 能独立完成“资料 → 候选 → 本体 → 映射 → 校验 → 评审 → 交付”。
- 客户能使用对象和查询理解交付结果，并追踪来源。
- 下一客户项目可引用已有行业资产和用例包，无需复制一套核心代码。
- 业务动作具备明确的参数、权限、校验和执行记录。
- 每次发布锁定依赖与审定产物；数据变化和 AI 重跑不能静默改变已发布本体。

效率以实际操作时间与返工率评估，不以图谱节点数量、生成字数或模板数量作为主要成功指标。

## 4. Foundry 参考与产品转化

Foundry 官方将 Ontology 描述为连接真实对象与数据的操作层，包含对象、链接、动作、函数与安全；Workshop 基于对象构建应用。[Ontology](https://www.palantir.com/docs/foundry/ontology/overview)、[Workshop](https://www.palantir.com/docs/foundry/workshop/overview)

| 参考模式 | 我们的实现 | 阶段 |
|---|---|---|
| Ontology Manager / 对象资源页 | 统一查看定义、样例、映射、来源、约束和依赖 | M1 |
| Ontology Proposal | 带基线版本的变更单、差异、审批和合并检查 | M1 |
| Object Explorer / Object View | 筛选对象、浏览关联和来源、保存查询、生成详情页 | M1 基础预览，M2 完整视图 |
| Workshop | 列表、详情、表单、任务、指标等共用组件形成 3 个配置模板 | M2 |
| Actions | 自有动作契约、预览、权限与前置校验、幂等和审计 | M2 沙箱，M3 内部任务 |
| Automate | 定时/对象条件触发内部待办或站内通知 | M3 |
| Workflow Lineage | 字段 → 映射 → 本体 → 查询/动作/应用的依赖影响 | M1 局部，M3 串联 |
| 资源与实例分层授权 | 分开控制模型定义、实例数据和动作执行权限 | M1 项目隔离，M3 细化 |

本体标准与运行契约分开：
- OWL/RDF/SHACL 用于语义表达、交换与声明约束的校验。
- ActionType、ObjectView、Automation、权限与事务行为属于自有 Operational Contract。
- 导出 OWL 不代表动作或 UI 同时可移植；完整运行交付还需要配置、版本和兼容运行时。

## 5. 用户、权限与使用模式

| 角色 | 主要任务 | 边界 |
|---|---|---|
| FDE | 需求梳理、接入、候选处理、建模、映射、提交发布 | 可编辑草稿；发布依项目规则授权 |
| 领域专家 | 确认定义、关联、例外与验收查询 | 默认业务审阅视图；实例访问另行授权 |
| 数据工程师 | 接入、剖析、身份对齐、映射调试 | 仅访问已授权数据范围 |
| FDE/项目负责人 | 排优先级、审批、验收、资产沉淀 | 指定评审人、发布人和数据负责人 |
| 客户管理员 | 配置目标环境、用户、备份与版本切换 | 仅管理本客户实例 |
| 客户操作用户 | 浏览对象、处理内部任务 | 使用已发布应用和获准动作 |
| 插件维护者 | 维护接口、插件和兼容性 | 安装插件权限与数据访问权限分开 |

工作台提供两个入口：
- FDE 构建模式：完整证据、模型、映射、验证和发布工具。
- 客户使用模式：仅显示对象、业务页面、内部任务和获准管理功能；隐藏引擎与插件实现细节。

M1 采用少量预置角色及项目成员权限；M3 增加按工厂/产线的实例范围及属性遮蔽。能查看模型定义不自动获得实例数据权限。

## 6. 首个用例与验收问题

默认从质量异常追溯开始，M0 与领域专家确认范围。

| 业务问题 | 涉及对象 | 可验收输出 |
|---|---|---|
| 某批次有哪些缺陷，关联哪个工单、工序和设备？ | Lot、Defect、Inspection、WorkOrder、Operation、Equipment | 关系链与每条来源 |
| 某设备在指定时间内关联哪些质量异常？ | Equipment、OperationExecution、Inspection、Defect | 时间过滤结果及样例对账 |
| 哪些高优先级缺陷未被处理，责任人是谁？ | Defect、Task、Person | 待办列表；早期使用固定样例，M3 使用内部任务 |

MVP 发布 3 个有人工标定期望结果的只读查询。第三个查询的“责任人/处理状态”来自样例或已授权数据，不提前承诺客户生产系统闭环。

每个用例记录业务目标、数据可用性、负责人、关键实体/关联、验收标准、排除范围和未决问题。验收问题是建模范围的依据。

## 7. 端到端工作流

~~~mermaid
flowchart LR
  A[用例与验收问题] --> B[证据与数据剖析]
  B --> C[AI候选与人工建模]
  C --> D[映射测试与对象预览]
  D --> E[校验与变更评审]
  E --> F[锁版与交付]
  F --> G[对象应用与内部任务]
  G --> H[监控与变更提案]
  H --> C
~~~

1. 建项目：选择场景模板，明确数据范围、目标环境与评审人。
2. 收证据：导入结构、样例与文字资料，标记授权范围。
3. 看画像：检查主键、重复、枚举、单位、缺失值与时间口径。
4. 出候选：规则/LLM 生成 Proposal，保留来源；领域判断由人员确认。
5. 建映射：预览对象/关系，使用测试样例调试转换与实体对齐。
6. 验证：结构、SHACL、映射测试、业务查询分别检查。
7. 提变更：绑定基线版本与差异，审批后合入并发布。
8. 交付：导出锁定包，检查目标环境，安装并执行验收脚本。
9. 沉淀：经脱敏与授权后将通用资产提交行业库。
10. 运营：数据漂移生成新提案；不会直接覆盖已发布语义。

## 8. 信息架构与 FDE 操作体验

顶部固定显示客户、项目、环境、本体/发布版本。切换项目后清除原项目查询和缓存，避免上下文混淆。

| 导航 | 核心内容 |
|---|---|
| 项目驾驶舱 | 用例、阶段、待办、未决问题、最近运行、交付清单 |
| 证据与数据源 | Evidence Inbox、连接器、字段画像、来源快照 |
| 本体与候选 | 类树、关系、表单/表格、候选队列、证据侧栏 |
| 映射与验证 | 源字段/目标属性、转换、样例、错误和测试 |
| 对象与应用 | 对象集、详情、保存查询、应用模板、动作预览 |
| 变更与发布 | Ontology PR、影响、评审、版本、环境和交付包 |
| 资产与设置 | 核心包、行业包、客户扩展、插件、成员、运行日志 |

MVP 优先实现表格和属性表单，关系图提供查看、选中与定位。复杂拖拽建模、图布局编辑和代码多视图同步不阻塞首版。

FDE 高频操作要求：批量改标签/约束、批量审核并保留逐项结果、搜索/筛选、返回上次位置、长任务进度与重试、未保存提示。M2 增加命令面板和快捷键；领域专家界面用中文业务术语，不要求阅读 RDF。

### 9.1 FR-01～FR-03：需求、证据、数据发现

- Requirement 包含待回答问题、业务负责人、重要性、验收查询和状态；支持关联本体、映射、测试与发布物。
- Evidence 包含原文/字段定位、来源标识、快照、时间、访问范围、抽取方法与人工确认。人工定义允许没有外部文件，但必须记录定义人和理由。
- CSV/XLSX 显示工作表、列、行号；文本显示段落/偏移；SQL 显示数据库/表/列及抽样运行标识。原始样本按权限留存，不默认复制完整生产库。
- PostgreSQL MVP 为只读发现与限量抽样，设置表白名单、行数、超时和查询取消。
- 画像至少有空值、唯一率估计、重复示例、枚举、疑似主键、日期范围与单位备注；抽样统计标明样本规模，不伪装成全量统计。
- M2 OpenMetadata 读取表、字段、标识与可用标签；血缘只展示实际能取到的部分。其元数据采集不等于已获得业务行数据，实例仍来自客户数据源。
- PDF/DOCX/OCR 不进入 M1；M2 若有余量可做可搜索文本文件解析，扫描件继续人工整理。

验收：需求可导航到相关模型及查询；已发布定义 100% 有证据或人工定义记录；常见概念两次点击内可定位授权范围内的来源。

### 9.2 FR-04～FR-05：候选与本体编辑

- 候选类、属性、关系和映射均先进入 Proposal，不能直接写入已发布版本。
- 显示理由、来源、相似概念、模型/模板版本、置信信息和影响；没有可靠分数时显示“未校准”，不把模型自评分当准确率。
- 接受、拒绝、合并、改名、人工锁定；修改合并规则后重新计算受影响候选。
- 中文名、英文名、客户现场叫法与稳定 API ID 分离。
- 编辑类、关系 domain/range、属性类型、枚举、单位、必填与基数约束；MVP 限定支持的 OWL/SHACL 子集，并导出能力清单。
- 对重复 ID、IRI 冲突、关系端点缺失、约束错误进行阻断；孤立概念、循环层级等按具体业务规则判定，不能一概当错。
- 不支持的导入语义必须报告；不能静默删掉复杂公理后声称完整导入。

验收：拒绝项不进入草稿；批量审核有逐项记录；人工锁定项不会被再次生成覆盖；支持子集导入导出语义对照通过。

### 9.3 FR-06～FR-08：映射测试与可运行预览

- MappingRule 保存源字段、目标、主键/关联键、转换、枚举与单位映射、空值策略、版本及测试样例。
- 对象身份采用项目/源系统/类型/稳定业务键组合；展示名不作为唯一键。
- 跨源实体合并需要明确映射或人工批准；同名、相近名称仅生成候选，不自动合并。
- 每条关键映射有输入/期望输出测试；错误定位 source、target、样本与原因，支持修复重跑。
- 默认转换只提供受控函数集；任意用户代码执行不进入 MVP。
- 100～1,000 条样例即时或任务式生成对象；列表筛选、关联导航、来源与本体版本可见。
- 保存查询条件、固定输入、预期对象/关系，作为客户演示和回归样例。
- 结构校验、SHACL 和业务正确性分别报告。SHACL 通过只表示满足声明约束，不能替代领域验收。

验收：关键标识/关联键映射完整；3 个标定查询匹配预期；重复运行不重复创建对象；所有映射失败可定位。

### 9.4 FR-09：Ontology PR 与生命周期

- MVP 使用基线版本 + 草稿变更集 + 乐观锁；支持差异、评论、责任人、提交、退回、批准和合并。
- 基线变化时拒绝旧变更直接合并；重新生成差异、解决冲突、运行检查并再次审批。
- 发布后的稳定 ID 不直接改名；业务展示名变更与 ID 迁移区别处理。
- 资源废弃必须有原因、替代项/无替代说明和受影响消费者；有依赖时不能静默删除。
- 模型发布前执行当前变更的校验、映射测试、业务查询和权限检查；审批后再改内容会使原审批失效。
- 评审周期和职责可按项目配置；MVP 无复杂流程设计器。

验收：过期审批、旧基线合并、未关闭阻断错误均被拒绝；拒绝或并发提交不改变已发布版本。

### 9.5 FR-10～FR-13：交付、复用、插件与基础治理

- Release 锁定本体、映射、样例、查询、插件与运行配置；导出前展示内容和敏感项。
- Preflight 检查缺失插件、版本、secret 引用、存储、模型选项、磁盘和数据源连通性；区分阻断/警告，不打印凭据。
- M1 使用开发受控环境 Compose；M3 增加离线安装所需镜像、依赖与完整安装路径。
- 资产采用基础核心 → 行业包 → 客户扩展；引用固定版本，禁止在客户包中静默覆盖公共概念含义。
- 通用资产回流需选择条目、移除实例/敏感信息、审核来源与复用权限。
- Cordis 提供加载、依赖与生命周期；项目、模型、连接器、UI 等能力经自有服务接口提供。
- M1 实现最小受信插件集合、配置校验、失败诊断和健康状态，不建设开放插件市场。
- 每次查询、导出、异步任务、制品下载均校验项目权限；日志、缓存、对象存储路径也带项目作用域。

验收：同一用例包导入新项目可重放；凭据不进入包；缺依赖不能发布；跨项目负向权限用例全部通过。

### 9.6 FR-14～FR-16：对象、应用和动作

M2 仅做 3 个共享组件模板：设备详情、质量异常收件箱、领域审核表单。它们复用列表、详情、时间线、指标与表单组件，通过属性绑定和布局配置生成，不能解释成 3 套独立业务系统。

- ObjectView 展示属性、关联、来源、时间线与质量；统计结果沿用相同数据权限。
- 应用上下文固定项目、对象类型和发布版本；链接跳转不丢失对象身份。
- 轻量能力映射让不同客户设备类型绑定到同一视图契约；先做字段/关系绑定，不实现完整接口多态运行时。
- ActionType 定义参数、作用对象、权限、前置条件、变更预览、结果与审计；M2 全部在隔离样例沙箱执行。
- M3 允许审批后创建/更新平台内部待办和处理备注；不声称改变 MES 的生产状态。
- Action 模拟、审批与执行绑定同一输入及对象版本；对象过期需重新检查。
- idempotencyKey 限定在项目、动作类型/版本作用域，保存输入、目标对象和审批上下文的请求指纹。相同键相同请求可返回原结果，但仍检查当前权限；相同键不同内容返回冲突且不执行。
- 失败/未知结果明确展示，禁止无条件重试副作用；新的输入或重新审批使用新的执行请求。
- 功能/API/表单共用相同动作服务，不能在 UI 中绕过校验直接修改对象。

验收：FDE 通过配置生成 3 个模板并演示 1 条质量处理链；无权限、校验失败和重复请求不产生错误变更。

### 9.7 FR-17～FR-20：试点与运营

- 只读定时批同步；新增字段、类型、枚举和主键变化产生 DriftProposal。
- 同步数据与改变本体分开；新增实例可按已发布映射进入数据面，模式变化需审批。
- 自动化首批只支持有限条件和内部任务/站内通知，具备去重窗口、启停与执行记录；邮件/外部通知后续单独接入。
- 对象权限先按工厂/产线范围过滤，属性策略支持隐藏/脱敏；搜索、聚合、导出、后台任务与缓存遵守同一策略。
- M3以依赖列表展示字段变化影响的映射、查询、视图与动作，来自真实登记关系；未覆盖依赖明确标为未知。交互影响画布后置，不阻塞试点。
- 健康页先展示数据新鲜度、映射失败、关键约束违规、未处理漂移、任务失败与运行成本摘要；完整趋势图后置。
- 客户使用部署和运维向导完成离线安装、查错、升级和版本切换。
- 客户用例包只打包所需应用和能力，不携带其他客户数据、凭据或本地草稿。

### 9.8 FR-21～FR-22：恢复与复制

- 备份覆盖控制数据库、审定产物、映射、实例检查点和必要的业务任务记录。
- 升级前验证兼容性和迁移方案；在演练环境验证恢复，不能只验证“备份文件存在”。
- 第二项目复制验证可在内部第二客户配置进行，但不能称为第二客户上线。
- 记录通用资产采用率、客户扩展数量、映射调试时间和核心代码变更量。
- 复制失败或需要修改核心时，建立产品缺口单；不得把大量客户硬编码称为插件化复用。

## 10. 产品架构与行业扩展策略

### 10.1 整体架构

产品分为**工具层**和**行业语义层**，两条线正交：

```
┌─────────────────────────────────────────────────────────────┐
│  行业语义层（按需加载）                                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │  制造业包    │  │  医疗包      │  │  金融包      │  ...  │
│  │  (IOF Core)  │  │  (SNOMED等)  │  │  (FIBO等)    │       │
│  └──────────────┘  └──────────────┘  └──────────────┘       │
├─────────────────────────────────────────────────────────────┤
│  工具层（跨行业通用）                                        │
│  建模 · 映射 · 验证 · 版本管理 · 发布 · 交付                 │
└─────────────────────────────────────────────────────────────┘
```

| 层次 | 说明 | 可扩展性 |
|------|------|----------|
| **工具层** | 本体建模、映射、验证、版本、发布、交付等能力 | 核心代码，不因行业变化 |
| **行业语义层** | 行业标准本体 + 概念模板 + 枚举值 + 用例包 | 按需加载行业包 |

### 10.2 行业包策略

每个行业包包含：
- 该行业的标准本体引用
- 行业特定的概念模板、关系模式、枚举值
- 该行业的典型用例包模板

| 行业 | 行业包 | 行业标准本体 | 状态 |
|------|--------|--------------|------|
| 离散制造 | `industry-manufacturing` | IOF Core | 首发（M1-M3） |
| 流程制造 | `industry-process` | 待定 | 规划（M5+） |
| 供应链 | `industry-supply-chain` | 待定 | 规划（M5+） |
| 其他 | 待定 | 待定 | 规划 |

行业包作为可选插件，不影响工具层功能。客户只需加载其所在行业的包。

### 10.3 IOF 定位

IOF（Industrial Ontologies Foundry）是**工业/制造业的标准本体库**，不是跨行业的通用本体。IOF 基于 BFO 扩展，提供工业场景的中层语义，包括：

- 工厂、产线、设备、产品、物料、批次等核心制造概念
- 工单、工序、执行、检验、缺陷等生产流程概念
- 与 BFO 顶层本体的映射关系

制造业包引用 IOF Core 作为行业基础，未来扩展其他行业时引入对应行业标准本体。

### 10.4 首个用例与验收问题

默认从**离散制造质量异常追溯**开始，M0 与领域专家确认范围。

| 业务问题 | 涉及对象 | 可验收输出 |
|---|---|---|
| 某批次有哪些缺陷，关联哪个工单、工序和设备？ | Lot、Defect、Inspection、WorkOrder、Operation、Equipment | 关系链与每条来源 |
| 某设备在指定时间内关联哪些质量异常？ | Equipment、OperationExecution、Inspection、Defect | 时间过滤结果及样例对账 |
| 哪些高优先级缺陷未被处理，责任人是谁？ | Defect、Task、Person | 待办列表；早期使用固定样例，M3 使用内部任务 |

MVP 发布 3 个有人工标定期望结果的只读查询。第三个查询的"责任人/处理状态"来自样例或已授权数据，不提前承诺客户生产系统闭环。

每个用例记录业务目标、数据可用性、负责人、关键实体/关联、验收标准、排除范围和未决问题。验收问题是建模范围的依据。

### 10.5 制造语义约束（首发行业包）

| 层次 | 本期范围 |
|---|---|
| 基础语义 | 稳定标识、组织/地点、时间、单位、来源、状态和责任 |
| M1 场景核心 | Plant、ProductionLine、Equipment、Product、Material、Lot、WorkOrder、Operation、OperationExecution、Inspection、Defect、Person、Task |
| M2 视图补充 | 维护记录与设备事件样例，依实际试点取舍 |
| 后续扩展 | 完整 BOM 版本、Routing、工艺版本、传感器原始时序、库存与计划 |

示例：WorkOrder 关联 Lot；OperationExecution 关联工单、工序、设备和起止时间；Inspection 关联批次与检验结果；Defect 关联检验与处理 Task。

工序定义与执行记录分开。跨时间、设备、物料批次的多方关系优先通过执行/观测对象表达，避免仅用一条无时间语义的关系表达全部事实。

- 数值保存单位/量纲；单位换算用审定规则，不能只修改展示单位。
- 时间记录业务时区，区分发生时间、有效时间与采集时间；班次日历属于客户配置。
- 保留源系统代码、版本与规范化值，不丢失原始标识。
- 质量缺陷、设备与批次的关键关联必须人工对账，禁止凭名称相似静默推定。
- 原始高频时序保留在源系统；图中保留观测摘要、事件和可追踪引用。
- 行业标准映射作为后续可选包，未经核验不宣称符合 ISA-95 等标准。

## 11. 核心产品对象与状态机

| 类别 | 对象 | 重要边界 |
|---|---|---|
| 项目 | Project、UseCase、Requirement、Decision | 范围、负责人、验收查询与未决事项 |
| 证据 | Source、SourceSnapshot、Evidence、ProfilingRun | 来源、定位、访问范围、抽样和留存 |
| 建模 | Ontology、OntologyVersion、Class、Property、Relation、Constraint | 类型定义/TBox；发布后不可变 |
| 候选 | Proposal、ModelRun、ReviewDecision | 建议与审定内容分开 |
| 数据 | MappingVersion、IdentityMapping、DatasetSnapshot、Object、Link | 实例/ABox 与本体版本分别管理 |
| 验证 | MappingFixture、ValidationRun、SavedQuery、ExpectedResult | 绑定输入、规则、版本和期望 |
| 运行 | ObjectView、ActionType、ActionRun、AutomationRule、Task | 自有操作契约，权限与执行记录 |
| 交付 | ChangeRequest、Release、UseCaseBundle、Deployment、PreflightReport | 制品身份与环境绑定分开 |
| 治理 | PluginInstallation、AuditEvent、DriftProposal、HealthSnapshot | 配置、日志、范围与影响 |

所有对象有稳定 ID、项目作用域与创建记录；适用对象额外具有来源、版本和审定信息。身份合并不直接删除原始 source IDs。

状态约定：
- 项目：发现 → 建模 → 验证 → 交付 → 支持 → 归档。
- 候选：待处理 → 接受/拒绝/合并；后续修改创建新记录。
- 变更单：草稿 → 已提交 → 需修改/已批准 → 已合并/已取消。
- 本体版本：草稿 → 已发布 → 已废弃；已发布内容不原地修改。
- 制品：已构建 → 已验证 → 可部署；每次部署另记目标与结果。
- 动作：草稿定义 → 可用定义；执行为预览 → 待审批（如配置）→ 执行中 → 成功/失败/结果待核实。

## 12. 本体、应用与包的版本规则

- 本体、映射、ActionType、ObjectView 独立版本化，由 UseCaseBundle 锁定组合。
- MAJOR：删除/改变稳定 ID、破坏类型/关联键、收紧约束导致旧数据不再合法、动作输入不兼容等。
- MINOR：兼容的新增概念、可选属性、查询或视图。
- PATCH：不改变行为的说明或展示修订；不能把所有 SHACL 修改都归为 PATCH。
- 基础包升级形成显式提案，展示客户扩展与映射影响；不自动更新所有客户。
- Cordis 配置 overlay 与本体语义扩展是两种机制：前者组合插件，后者需语义兼容检查。
- 发布版本切换、实例数据恢复、业务动作补偿分别处理；切换旧版本不意味着历史业务操作被撤销。

## 13. 技术架构与稳定边界

~~~mermaid
flowchart TB
  UI[FDE工作台 / 客户应用] --> API[受控API与权限]
  API --> C[Cordis：组合服务与插件]
  C --> J[持久任务与Workers]
  C --> P[(项目 / 版本 / 审计存储)]
  J --> S[Python语义服务 / Semantica适配器]
  J --> X[数据连接器 / OpenMetadata只读适配]
  S --> G[(实例与图查询存储)]
  S --> A[(审定产物与来源快照)]
  C --> O[对象查询 / 动作 / 视图服务]
  O --> G
  O --> P
~~~

- Cordis：依赖注入、生命周期、服务注册与事件组合。采用哪个分发包/版本在 M0 实测锁定；不默认直接依赖 DeepSeek Harness 的所有内部包。
- Semantica：通过自有接口封装候选生成、图构建与本体相关能力；实际支持范围由 M0 固定样本验证。平台评审、版本、权限和交付不假设由 Semantica 自动提供。
- OpenMetadata：M2 可选只读连接器；核心工作台没有它仍可运行。不将任意业务关系伪装成其技术数据血缘。
- 控制存储：PostgreSQL；MVP 使用一个支持目标查询/校验的图存储实现，M0 确认。产物先用挂载目录及存储接口，不强制部署额外对象存储集群。
- 任务：MVP 可用持久任务表和 Worker；跨进程持久状态不由内存事件总线替代。
- UI：共享组件与受信模块注册；Cordis 服务树不会自动解决浏览器布局或前端权限问题。

## 14. 插件与服务契约

首批服务：ProjectService、EvidenceService、Connector、Mapper、OntologyService、Validator、QueryService、ReviewService、ReleaseService；M2 扩展 ViewService、ActionService。

插件最小声明：id、version、apiVersion、provides、requires、配置 schema、运行模式、权限需求、健康检查、兼容范围。客户 profile 锁定插件版本，secret 仅使用引用。

设计约束：
- 能力通过稳定服务键与 typed events 访问，业务插件不读取另一插件的私有表或具体实现。
- 权限/审计虽可配置为插件实现，缺失时业务 API 必须停止服务，不能通过卸载绕过。
- 长任务事件有 projectId、runId、correlationId、idempotencyKey；持久执行需检查点、超时、取消和重试。
- 卸载应清理注册、监听器、连接和定时器，并先处理在途任务。
- Cordis disposal 不自动撤销已提交数据库事务、通知或远程调用。
- 权限 manifest 不是代码沙箱。同进程仅运行受信内置/团队插件；不可信插件的隔离执行另立范围。
- 存储或有迁移的插件升级采用排空/维护窗口；“一切可插件化”不等于所有组件都能无损热替换。

## 15. 动作、自动化与系统写回边界

M2 动作只对沙箱快照生效；M3 仅持久化平台内部任务、意见和处理状态。业务页面必须区分“平台记录”和“源系统状态”。

未来接入客户系统写回需独立设计写回插件，包含显式授权、最小作用域、幂等、执行结果核对、未知结果处理和补偿策略。不承诺跨 MES、ERP 与本平台的分布式原子事务。

M3 自动化只调用获准的内部动作；具备条件预览、去重、执行日志和暂停开关。自动化代码不直接修改实例存储。

## 16. 发布与用例包规范

~~~text
manifest.json                 包ID、版本、依赖、哈希、能力与环境要求
ontology/                     OWL/Turtle、JSON-LD、词表、命名空间
validation/                   SHACL、映射测试、业务查询期望与报告
mappings/                     版本化字段/身份/单位/枚举规则
queries/                      保存查询与固定样例
evidence/                     获准导出的来源索引与审定记录
views/                        M2起：详情页与模板配置
actions/                      M2起：动作定义；不含生产凭据
automation/                   M3起：内部条件/效果配置
runtime/                      插件锁定、Compose、secret占位
governance/                   变更说明、审核记录、依赖清单
runbook/                      安装、检查、升级、恢复、交接
~~~

M1 manifest 可包含为空的后续能力目录。客户数据默认不随包导出；完整离线包按许可证和客户许可打包所需镜像/依赖，本地模型另列资源条件。

可复现性分三类：
1. 制品完整性：验证每个实际文件和镜像的哈希。
2. 确定性语义重放：锁定已审定本体、映射、固定输入与工具版本；比较规范化图/查询结果，处理 RDF 空白节点和序列化顺序。
3. AI 回归评估：保存模型标识、提示、原始响应与采纳记录；重新调用模型允许产生不同候选，以质量基线评估，不要求相同哈希。

构建时间、压缩包时间戳不作为语义相同的判断依据。

## 17. 非功能需求与安全

| 项目 | 基线要求 | 验收阶段 |
|---|---|---|
| 项目隔离 | API、后台任务、制品、缓存和日志授权一致 | M1 |
| 可追溯 | 审定定义与关键映射有证据或人工决定 | M1 |
| 密钥 | 使用引用与受控注入；无普通日志/包内明文 | M1 |
| AI 数据范围 | 项目明确允许的数据/模型；可停用外部模型 | M1 |
| 文档与导入 | 文件大小/类型限制；提取内容视为不可信资料 | M1 |
| 失败恢复 | 持久任务、重试幂等、可定位错误 | M1基础，M3批同步 |
| 实例/属性授权 | 工厂/产线过滤，敏感属性遮蔽；覆盖搜索与导出 | M3 |
| 离线能力 | 在断外网环境完成安装、查询和内部任务；模型缺失有手工路径 | M3 |
| 发布兼容 | 依赖锁定、迁移检查、旧版绑定/恢复演练 | M1基础，M4完整 |
| 插件供应 | 受信包白名单、依赖清单和来源校验；离线发布签名验证 | M4 |
| 运维恢复 | 目标RPO≤24小时、RTO≤2小时；受测数据规模见里程碑 | M4 |

性能统一基准：8 vCPU、32 GB RAM、SSD、单节点、固定图存储与数据集版本；无外部 LLM 的映射/校验和查询单独测量。M1 1,000 个实例完成测试闭环；M3 10,000 个对象、约 100,000 条三元组作为目标上限基准；M4 目标为预定义查询 P95≤2秒、映射与校验≤10分钟。

M0冻结基准协议：5个并发请求Worker，以固定比例轮询3个查询；预热2分钟后持续至少10分钟且收集至少1,000次请求。记录吞吐、错误/超时率与延迟，不丢弃失败请求掩盖结果；固定无故障基准要求错误/超时0，故障注入另测。映射/校验计时从读取固定输入快照到验证报告持久化，不计LLM调用。若实测不满足，发布容量上限与原因，并重新评审指标；不可无记录地视为通过。

## 18. 产品指标与验收口径

| 指标 | 目标/门槛 | 定义 |
|---|---|---|
| 创建项目 | ≤10分钟，M1 | 模板和权限就绪后的主动操作时间 |
| 首个可评审版本 | ≤1个工作日，M1 | 固定脱敏基准；记录主动操作与等待分别耗时 |
| 效率改善 | ≥50%，M3观察目标 | 相同范围对比手工基线；不作为未采样前的承诺 |
| 证据完整性 | 100%，发布门槛 | 发布类/关系/关键映射有来源或审定理由 |
| 关键映射 | 100%，发布门槛 | 需求清单中的关键标识和关联键都有验证映射 |
| 非关键字段覆盖 | ≥90%或明确豁免 | 分母为用例约定字段，不是整个数据库 |
| 关键业务正确性 | 100%人工期望匹配 | 3个标定查询；M3另抽检100条关键对象/关系 |
| 候选接受率 | M1建立基线 | 辅助优化指标；不能靠少报候选冒充质量提升 |
| 交付重放 | 固定输入结果一致 | 用审定快照，不重新调用LLM来判断 |
| 版本切换 | ≤10分钟，M3 | 切换本体/映射/视图绑定，不含数据恢复和外部补偿 |
| 复制效率 | 核心代码零客户分叉，M4 | 第二项目通过包与配置复用 |
| 复用比例 | ≥40%，M4观察目标 | 审定可复用定义/映射占项目适用资产比例 |

未满足质量/权限/恢复门槛不能发布；效率与复用目标先记录基线、诊断原因，再调整产品。统计必须附样本、范围和运行条件。

## 19. 里程碑总览

详细工作包、Owner、依赖和演示剧本见 [MILESTONES.md](MILESTONES.md)。所有阶段初始状态为“未开始”。

| 阶段 | 周期 | 可用结果 | 关键验收 |
|---|---|---|---|
| M0 技术与产品闸门 | W1–2 | 锁定用例、接口、样本与技术能力 | CSV到审定本体/SHACL/导出；插件生命周期验证 |
| M1 FDE内部MVP | W3–10 | 建模、证据、映射、评审、对象预览与交付闭环 | 2名非开发FDE独立完成固定项目 |
| M2 对象应用MVP+ | W11–14 | 3个共用组件模板、动作沙箱、OpenMetadata只读 | 配置生成页面，1条沙箱业务链 |
| M3 客户试点 | W15–20 | 1客户/1用例/2数据源，内部任务与离线交付 | 客户验收、安装升级、连续2周观察 |
| M4 受控生产基线 | W21–24 | 恢复、兼容、安全、性能与复制证据 | 严重缺陷清零，恢复通过，第二项目复制 |

M4 是明确容量、受信插件和支持范围下的生产基线。自动生产写回、实时 IoT、公有 SaaS、通用 App Builder 进入 M5+ 候选池，需要真实需求与独立投入评估。

## 20. 发布门槛、测试与风险

发布顺序：契约校验 → 映射测试 → SHACL → 业务验收查询 → 权限负例 → 人员审批 → 制品检查 → 目标环境检查。新内容或新基线会使相关结果失效。

测试重点：
- 契约与兼容：版本化 schema、错误码、稳定 ID 与支持的语义子集。
- Golden Corpus：首个质量追溯样本及设备/审核模板；只在实际支持范围内回归。
- 生命周期与故障：依赖缺失、卸载、重试、取消、断点、重复事件、过期审批。
- 安全：跨项目、属性泄漏、secret、导入内容注入、导出和后台任务授权。
- 业务：标识/关联、单位、时间、人工审定查询、数据漂移不覆盖本体。
- 交付：新环境重放、离线安装、升级失败、备份恢复与第二项目复制。

| 风险 | 负责人 | 处置 |
|---|---|---|
| 引擎能力与文档不一致 | 语义负责人C | M0实测；替换适配器或缩小支持子集，更新范围 |
| 插件/服务过度抽象 | 技术负责人B+D | 一个真实实现起步；验证可替换性而非预做市场 |
| 关键身份/业务关系错配 | 领域专家+C | 阻断发布；人工对账，不能靠整体95%通过掩盖 |
| 客户接入延误 | 产品/FDE负责人+D | 固定样例继续开发；客户验收不得标记已过 |
| 文档/UI范围过大 | 产品/FDE负责人+A | 按里程碑削减候选项，保闭环 |
| 副作用/回滚混淆 | B+D | 内部动作限定；版本、数据恢复和补偿分别验证 |
| 跨客户资产泄漏 | B+项目负责人 | 权限、导出和资产回流检查 |
| 规模/性能未知 | C+D | 固定基准实测，记录容量上限和部署条件 |

## 21. 启动与评审决策

启动时完成以下确认；未确认项沿用第2节的规划假设开展可独立推进的工作：

- 确认实际工程人数与产品/专家可用时间，据此重排里程碑。
- 确认首个客户用例、数据负责人和3个验收问题。
- M0锁定Cordis分发版本、Semantica支持范围、一个图存储和一个模型接口。
- 明确客户是否需断外网、本地模型、何时可只读接入。
- 确认第一批可沉淀的行业资产及客户复用授权范围。

需求变更进入变更表，列出影响的 FR、里程碑、人员周和替换范围；未批准的新增需求不会自动增加到24周基线。
